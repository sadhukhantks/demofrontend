# Jute Production — Waste Entry (proposed)

Last verified: 2026-08-10

> Scope: complete design specification for the **Jute Waste Entry** page under Jute Production
> and its **Wastage Area Master** (§12). Records the quantity of process waste generated by a
> department in a given **wastage area** on a given (date, spell), optionally attributed to a
> machine. The waste type is an **item** of item type 3 ('jute wastage') — see §9.
> This is a **SPEC SHEET + implementation contract**. Persona: **Portal**
> (`Depends(get_tenant_db)` + `get_current_user_with_refresh`, `{"data": …}` responses,
> soft delete via `active = 0`, **no approval workflow**).
>
> **ASSUMPTIONS — confirm before this reaches production.** No prior spec, table, endpoint,
> or precedent for waste capture existed in either repo when this was written (greenfield).
> The design below was derived from the closest structural analogue, Stoppage Hours
> (`../stoppage-hours/SPEC.md`). Specifically assumed:
> 1. Waste is recorded **per department per spell per day**, with machine attribution optional.
> 2. Waste type is an **item** (`item_mst.item_id`) whose group carries
>    `item_grp_mst.item_type_id = 3` ('jute wastage') — see §9. (Originally shipped as a fixed
>    app-level enum; reworked 2026-08-09 while the table was still empty on every tenant.)
> 3. Quantity is a **weight in kilograms**, `DECIMAL(10,3)`.
> 4. Waste is an **event log** — many rows per (dept, date, spell) are expected and allowed.
> 5. It is a **standalone record**: it does NOT post to inventory, does NOT create an
>    `item_mst` stock movement, and does NOT reconcile against production output.
>    (Item-linked / inventory-posting waste would be a materially larger scope — see §11.)

---

## 1. Overview

Jute Waste Entry is a daily entry page. An operator picks a **date** and **spell**, selects the
**department** (spreader, drawing, spinning, winding, beaming, weaving, finishing), optionally
narrows to a specific **machine**, chooses the **waste type**, enters the **quantity in kg** plus an
optional **remark**, and saves. Each save is one waste record; the page shows a grid of all waste
recorded for the selected date so the operator can review, edit, and delete rows for that day.

The business purpose is to quantify process loss per department and per shift so that waste
percentage against production can be reported later.

---

## 2. Goal & business rules

- **Type-tagged waste.** Every row carries exactly one waste item (`item_id`) drawn from
  `item_mst`, restricted to groups of item type 3 ('jute wastage') — see §9.
- **Event log, not a unique key.** Multiple waste rows per
  `(dept_id, tran_date, spell_id, item_id)` are allowed and expected (e.g. waste booked
  separately per machine within the same department and spell).
  **No unique constraint** — the table is an append/soft-delete log.
- **Department is stored** (unlike Stoppage Hours, where it is a UI filter only). Waste is
  fundamentally a departmental measure: it is frequently collected in bulk for a department with
  no single machine responsible, so `dept_id` is `NOT NULL` and `machine_id` is `NULL`-able.
- **Wastage area is required** (added 2026-08-10). Every row carries a `wastage_area_id` from
  `wastage_area_mst` (§12) and `wastage_area_mst.dept_id` MUST equal the submitted `dept_id` —
  the area picker cascades off Department exactly as Machine does. The column is `NULL`-able in
  the DB only so rows booked before the master existed remain valid; the API requires it on
  create AND on edit (an edit that would leave a legacy row area-less is a 400).
- **Machine is optional attribution.** When supplied, `machine_mst.dept_id` MUST equal the
  submitted `dept_id` — the API rejects a machine/department mismatch (§10).
- **Branch is derived on insert** from `dept_mst.branch_id` when the client omits it; reads
  tolerate legacy NULLs via `COALESCE`.
- **Validation:**
  - `waste_qty > 0` (a zero or negative waste row is meaningless — reject, do not silently store).
  - `waste_qty <= 99999.999` (enforced by the column width; the API returns 400 rather than
    letting MySQL truncate).
  - `item_id` must be an **active** item whose group has `item_type_id = 3` and belongs to the
    caller's `co_id` (§9) — one query doubles as existence + type + company-scope guard.
  - `spell_id` must exist in `spell_mst`.
  - `dept_id` must exist in `dept_mst`.
  - `wastage_area_id` must be an **active** area of the caller's `co_id` whose `dept_id` equals
    the submitted `dept_id` (§12) — one query doubles as existence + active + company + dept guard.
  - `tran_date` must not be in the future.

## 3. Page UX

**Header title:** `Waste Entry` (under Jute Production).
**FE page:** `src/app/dashboardportal/juteProduction/wasteEntry/page.tsx`.
**Persona scope:** `co_id` + `branch_id` consumed from `useSidebarContext()` exactly as the
spreader / stoppage pages do (multi-branch auto-resolution from `selectedCompany?.branches`).

### 3.1 Entry form + day grid columns

| # | Column | Control | Stored? | Notes |
|---|--------|---------|---------|-------|
| 1 | Date | DatePicker | ✅ `tran_date` | Defaults to today; drives the grid reload |
| 2 | Spell | Select | ✅ `spell_id` | From `spell_mst` (active) |
| 3 | Department | Select | ✅ `dept_id` | From `dept_mst` for the selected branch |
| 4 | Wastage Area | Select | ✅ `wastage_area_id` | Cascades off Department; required (§12) |
| 5 | Machine | Select (optional) | ✅ `machine_id` | Cascades off Department; blank = department-level waste |
| 6 | Waste Type | Select | ✅ `item_id` | Items of item type 3, 'jute wastage' (§9) |
| 7 | Quantity (kg) | Number | ✅ `waste_qty` | `> 0`, 3 decimal places |
| 8 | Remarks | Text (optional) | ✅ `remarks` | 255 chars |

**Every select on this page is searchable** (MUI `Autocomplete`, type-to-filter) — including
the page-level Branch picker. `renderOption` sets an explicit key because tenants carry
duplicate display names.

**Cascade reset:** changing **Department** clears both the selected **Wastage Area** and
**Machine**.
**Grid:** lists all active rows for `(co_id, branch_id, tran_date)` with edit + delete row actions,
and a footer total of `waste_qty` grouped by waste type.

## 4. Table DDL

Target tenant DB: `dev3`.

```sql
CREATE TABLE jute_prod_waste_entry (
    waste_entry_id      INT           NOT NULL AUTO_INCREMENT,
    co_id               INT           NOT NULL,
    branch_id           INT           NULL,
    tran_date           DATE          NOT NULL,
    spell_id            INT           NOT NULL,
    dept_id             INT           NOT NULL,
    wastage_area_id     INT           NULL,          -- required by the API, see §12
    machine_id          INT           NULL,
    item_id             INT           NOT NULL,
    waste_qty           DECIMAL(10,3) NOT NULL,
    remarks             VARCHAR(255)  NULL,
    active              TINYINT       NOT NULL DEFAULT 1,
    updated_by          INT           NULL,
    updated_date_time   TIMESTAMP     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (waste_entry_id),
    KEY idx_waste_co_branch_date   (co_id, branch_id, tran_date),
    KEY idx_waste_dept_date_spell  (dept_id, tran_date, spell_id),
    KEY idx_waste_machine          (machine_id),
    KEY idx_waste_spell            (spell_id),
    KEY idx_waste_area             (wastage_area_id),
    CONSTRAINT fk_waste_dept    FOREIGN KEY (dept_id)    REFERENCES dept_mst    (dept_id),
    CONSTRAINT fk_waste_machine FOREIGN KEY (machine_id) REFERENCES machine_mst (machine_id),
    CONSTRAINT fk_waste_spell   FOREIGN KEY (spell_id)   REFERENCES spell_mst   (spell_id),
    CONSTRAINT fk_waste_area    FOREIGN KEY (wastage_area_id) REFERENCES wastage_area_mst (wastage_area_id)
);
```

Rollback: `DROP TABLE IF EXISTS jute_prod_waste_entry;`

> Shipped originally with `waste_type_code VARCHAR(20)`; migrated to `item_id INT NOT NULL` by
> `dbqueries/migrations/alter_jute_prod_waste_entry_item_id.sql` (applied dev3 2026-08-09; run on
> sls and any other tenant carrying the table **together with the code deploy**).
>
> `wastage_area_id` added 2026-08-10 by
> `dbqueries/migrations/alter_jute_prod_waste_entry_wastage_area.sql` (applied dev3 + sls; run on

No `created_by` / `created_date` columns — audit is handled by DB triggers per repo convention.

## 6. API surface

Router prefix **`/api/juteWasteProd`**, file `src/juteProduction/waste_entry.py`,
queries in `src/juteProduction/waste_query.py`. Five entry endpoints mirroring
`stoppage_entry.py`, plus three for the area master (§12) on the same router:

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/entry_create_setup` | Dropdown options: spells, departments, machines, wastage areas, waste types |
| POST | `/entry_create` | Insert one waste row |
| GET | `/entries_by_date` | All active rows for `(co_id, branch_id, tran_date)` |
| PUT | `/entry_edit/{waste_entry_id}` | Update one row (requires `?co_id=`) |
| DELETE | `/entry_delete/{waste_entry_id}` | Soft delete `active = 0` (requires `?co_id=`) |
| GET | `/area_list` | Wastage areas for `(co_id[, branch_id])`, **including inactive** |
| POST | `/area_create` | Insert one wastage area |
| PUT | `/area_edit/{wastage_area_id}` | Replace one wastage area (requires `?co_id=`) |

### 6.1 Company scoping on the by-id path (security-relevant)

`/entry_edit` and `/entry_delete` **require `co_id` as a query param** and locate the row by
`(waste_entry_id, co_id)`, never by primary key alone. A tenant DB holds every company's rows,
so a PK-only lookup would let a user scoped to company A mutate company B's row by guessing an
id. A row belonging to another company returns **404**, not 403 — it must not be distinguishable
from a row that does not exist. The `co_id` predicate is on **both** the guard SELECT and the
UPDATE itself, so the check cannot be lost if the two drift apart.

> Note: `stoppage_entry.py` — the precedent this feature is modelled on — locates rows by PK
> alone and has the same gap. It was left unchanged here (wider blast radius, separate
> decision) but is worth a `tenant-auditor` pass. This feature deliberately diverges from the
> precedent on this point.

**Editable fields:** `spell_id`, `wastage_area_id`, `machine_id`, `item_id`, `waste_qty`,
`remarks`. `dept_id` and `tran_date` are **immutable** — delete and re-add to move a row to
another department or date, which keeps the branch derivation clean. Area and machine changes
are re-validated against the row's **existing** `dept_id`, so the §10 guard cannot be
sidestepped via edit. On edit, a `null` field means "leave unchanged"; there is currently
**no way to clear** an already-set `machine_id` (delete + re-add instead). The one exception is
`wastage_area_id`: because it is mandatory, an edit whose resolved value would still be `NULL`
(a legacy row, no area supplied) is rejected with a 400 rather than saved area-less.

`/entry_create_setup` takes `co_id` (required) and `branch_id` (optional) and returns:

```json
{
  "data": {
    "spells":      [{"spell_id": 1, "spell_name": "A", "working_hours": 8.00}],
    "departments": [{"dept_id": 3, "dept_desc": "Spinning", "branch_id": 4}],
    "machines":    [{"machine_id": 11, "machine_name": "Frame 1", "dept_id": 3}],
    "wastage_areas": [{"wastage_area_id": 40, "area_name": "Card Floor", "dept_id": 3, "branch_id": 4}],
    "waste_items": [{"item_id": 5001, "item_name": "Hard Waste", "item_code": "1234"}]
  }
}
```

Machines **and wastage areas** are returned for the whole branch with their `dept_id` so the FE
can cascade client-side without a second round trip.

## 7. Error handling

Per repo convention: GET → `HTTPException` re-raise / `ValueError` 400 / `Exception` 500.
POST/PUT/DELETE → `db.rollback()` then raise / 500. All handlers are plain `def`
(sync-handler policy); JSON bodies read via Pydantic models, never `await request.json()`.

## 9. Waste type source (items of item type 3, 'jute wastage')

The dropdown is fed from `item_mst`, not an enum (reworked 2026-08-09):

```sql
SELECT im.item_id, im.item_name, im.item_code
FROM item_mst im
INNER JOIN item_grp_mst ig ON ig.item_grp_id = im.item_grp_id
WHERE im.active = 1 AND ig.item_type_id = 3 AND ig.co_id = :co_id
ORDER BY im.item_name
```

`item_type_master` row 3 = 'jute wastage' (`JUTE_WASTAGE_ITEM_TYPE_ID` in
`src/juteProduction/constants.py`). `item_mst` has **no `co_id`** — company scope travels via
`item_grp_mst.co_id` (known pitfall). Writes are validated by the same join
(`verify_waste_item_query`), so a non-wastage or foreign-company item is a 400. The day grid
LEFT-joins `item_mst` so a later-deactivated item still renders on historical rows. Mills manage
the list themselves via the Item master (e.g. sls has a 'Wastage' group with its own items).

## 10. Derivations & guards

- **branch_id on insert:** if the client omits `branch_id`, derive it as
  `SELECT branch_id FROM dept_mst WHERE dept_id = :dept_id`.
- **machine/department guard:** if `machine_id` is supplied, verify
  `machine_mst.dept_id = :dept_id AND machine_mst.active = 1`; otherwise 400.
- **area/department guard:** verify
  `wastage_area_mst.dept_id = :dept_id AND co_id = :co_id AND active = 1`; otherwise 400.
  Unknown, inactive, foreign-company and wrong-department areas all collapse to one message.
- **Reads** use `COALESCE(w.branch_id, d.branch_id)` so rows written before a branch was
  resolvable still surface on the correct branch.

### 10.1 Master-table column realities (verified against `src/models/mst.py`)

The three referenced masters do **not** all carry the conventional `active` flag. Verified:

| Table | Soft-delete flag | Consequence for this feature |
|-------|------------------|------------------------------|
| `spell_mst` | **none** — uses `status` (Integer, default 1) | Filter the spell dropdown on `status = 1`, **not** `active = 1` |
| `dept_mst` | **none at all** | Department dropdown can only be scoped by `branch_id`; no soft-delete filter exists |
| `machine_mst` | `active` (Integer) | The §10 machine guard works exactly as written |

`dept_mst`'s full column list is `dept_id, branch_id, dept_desc, dept_code, order_id,
created_by, created_date` — note it is **branch-scoped, not company-scoped** (no `co_id`),
which is why `branch_id` derives from the department rather than the other way round.

## 11. Deferred / out of scope

- **Inventory posting.** Waste is not booked as an `item_mst` stock receipt. If waste must
  increase jute-waste stock (item types 2/3), that is a follow-up requiring an issue/receipt
  document, not an extension of this table.
- **Waste % against production.** The read model that divides waste by the department's
  production for the same (date, spell) is deferred — the production side lives in different
  per-department tables (`spreader_prod_entry`, `jute_prod_spinning_*`, weaving/winding) with
  no common unit, so a unified denominator needs its own design.
- **Approval workflow.** None. Consistent with every other jute-production daily entry page.
- **Deleting a wastage area.** The master has no delete — `active = 0` disables an area (it
  stops appearing in the entry picker) while historical waste rows keep resolving its name.
- **Waste-by-area reporting.** The column is captured but no report groups on it yet.

## 12. Wastage Area Master (added 2026-08-10)

The areas the entry page's **Wastage Area** dropdown is fed from. Each area belongs to exactly
one department, and therefore to one branch.

**FE page:** `src/app/dashboardportal/juteProduction/masters/wastageArea/page.tsx`
(menu `Wastage Area Master`, path `juteProduction/masters/wastageArea`).
**Branch scoping:** identical to the entry page — a single sidebar branch is adopted
automatically, several means the operator picks one before anything loads. The dialog therefore
has **no branch field**: the page's branch is what gets stored.

```sql
CREATE TABLE wastage_area_mst (
    wastage_area_id   INT          NOT NULL AUTO_INCREMENT,
    co_id             INT          NOT NULL,
    branch_id         INT          NOT NULL,
    dept_id           INT          NOT NULL,
    area_name         VARCHAR(100) NOT NULL,
    active            TINYINT      NOT NULL DEFAULT 1,
    updated_by        INT          NULL,
    updated_date_time TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (wastage_area_id),
    UNIQUE KEY uk_wastage_area_name (branch_id, dept_id, area_name),
    KEY idx_wastage_area_co_branch (co_id, branch_id),
    KEY idx_wastage_area_dept (dept_id),
    CONSTRAINT fk_wastage_area_dept FOREIGN KEY (dept_id) REFERENCES dept_mst (dept_id)
);
```

Migration `dbqueries/migrations/create_wastage_area_mst.sql` (applied dev3 + sls 2026-08-10).
Rollback: `DROP TABLE IF EXISTS wastage_area_mst;`

**Why `branch_id` is stored rather than derived:** `dept_mst.branch_id` is nullable, so deriving
would strand areas whose department has no branch. The reverse risk — an area filed under branch
A with a branch-B department, which would be invisible in the entry picker (read by branch) yet
still pass the dept-keyed write guard — is closed by an explicit guard on create and edit:
`dept_mst.branch_id`, when not NULL, must equal the submitted `branch_id`.

**Write rules:**
- `area_name` is trimmed, required, max 100 chars.
- `(branch_id, dept_id, area_name)` is UNIQUE; the API answers a collision with a 400 rather
  than surfacing MySQL 1062 through the 500 handler. The edit path excludes the row being
  edited from that check.
- `area_edit` requires `?co_id=` and locates the row by `(wastage_area_id, co_id)` — another
  company's area is a 404, per §6.1.
- Re-parenting an area to another department is allowed (a typo at creation is otherwise
  unfixable). Historical waste rows keep pointing at the same area row.

**Menu:** `dbqueries/migrations/seed_wastage_area_master_menu.sql` seeds `menu_mst` and grants
the new menu to exactly the roles that already hold `Waste Entry` in that tenant.
Applied dev3 + sls 2026-08-10.
